# Execution

How work runs: what gets delegated, how agents are briefed and checked, and the phases a piece of work moves through. **For open work — anything still needing a shape decided — the `team` skill runs on top of this and is the default; load this alone when the task is already planned and clearly shaped.** Generic mechanics only — it deliberately does not cover a repo's own artifacts, gates or commands, which live in its instruction files and project skills. **If this workspace has its own execution layer, read that too** and apply it on top of this. Written for an Opus 5-class main loop, so most of what follows is restraint, brief quality and trust boundaries — not encouragement to delegate or to self-check.

**What belongs in this file, for whoever edits it next:** would a round need it with no lifecycle around it, and would a solo shaped task need it with no round? Both, and it lives here; only one, and it belongs in that one — `team`, or whatever layer this workspace puts over either.

## Delegate by default

Two reasons, and the order matters. **Legibility first:** the main loop should carry decisions, results and whatever genuinely needs a human, not mechanics, so the person reading along sees headlines and judgement calls instead of diffs. **Context economy second:** reading is what spends main-loop context, so pushing it into agents lets a session run far longer before it must be compacted. Investigation and implementation both belong in an agent, and so does every research, design and review pass, even a short one: the inline carve-out below covers lookups and edits, not work that ends in a judgement. Where such a pass leans on context from this conversation, brief that in rather than keeping the pass. What comes back is conclusions, findings and open questions; the detail behind them stays in the agent's thread.

- **Stay inline** for what is cheap to do and expensive to explain: single lookups and reads, one-line edits, and small changes whose correctness depends on context accumulated in this conversation. When the two pull apart, the precedence is: small AND context-dependent stays inline; anything else delegates, including a context-dependent change big enough to produce a diff worth reviewing (brief it with the context it needs).
- **Cap fan-out** to what you can meaningfully review — parallel agents you skim-approve are worse than fewer you actually check.
- **Prefer one agent doing several related things** to several doing one thing each. Every spawn costs a full brief in and a full report out; batching pays that once and lets the agent reuse what it has already loaded.
- **Give each unit of work its own checkout, branched from the current base, and keep the tree you branch from clean** — whether or not you think lanes are running in parallel, since work is usually in flight in several places and the session that judges itself the only writer is the one that collides. It also keeps the base tree fast-forwardable. Any mechanism that yields one clean tree per unit will do; a project may fix the layout.
- **Sequential by default; parallel only when file-disjoint** (or isolated, e.g. separate worktrees), with explicit write territory per agent, and never start an implementer while the assessment gating it is still out. Parallel lanes also contend for the machine: run wall-clock-sensitive gates while other lanes are idle, and suspect the machine before the code when a slow test fails alone. **File-disjoint is not sufficient in a shared working tree the moment anything commits**: a pre-commit framework stashes the *whole* unstaged tree, runs the hooks and restores, so an interrupted cycle silently reverts another lane's in-flight edits, which reads as the model undoing its own work. Serializing commits does not fix it; either no lane commits until all are done, or each lane gets its own worktree. **Worktrees still share the stash list**, so a lane in a worktree never uses `git stash`; it keeps WIP as a commit or a patch file.
- **Never edit files in a checkout an agent is working in** — not even a doc it isn't touching. Its `git add` sweeps up whatever is dirty, so your write lands inside its commit under its message, and you find out from the log afterwards. Wait for it to finish, or edit somewhere else.
- **Move the session into the checkout whose work is now yours**, rather than aiming every command at it with `-C`: the session's directory is what the status line names and what default-path reads, diffs and writes resolve against. Move in when an agent hands the checkout back, not while it is still writing there. A plain `cd` outside the session's roots is reset by the harness, so use the harness's worktree tool (`EnterWorktree` with `path`); switching straight from one worktree to another is refused unless it sits under `.claude/worktrees/`, so step back with `ExitWorktree` (`keep`) and enter the next.
- **A fresh worktree has none of the repo's gitignored local config**, so it usually isn't runnable until that is set up — copy it across (without reading secrets) rather than reading absence as a defect. An agent that finds a file missing there has found what "untracked" means, not a deletion.
- **Continue an existing agent by default; spawn fresh only when inherited assumptions are the risk.** A ticket's work and its recurring chores (rebases, fix passes after review, CI watching) go to one long-lived worker continued by message, since every fresh spawn pays for a new brief. Reviewers stay fresh, and say so in the brief ("don't inherit my framing; concluding *keep it as it is* is legitimate"), or they just agree with you. A *fork* inherits the whole conversation, blind spots included, so a fork asked to review is the same opinion again; reserve forks for work that genuinely continues the thread, which also keeps a long session from copying a large context N ways (what OOM-kills the process). **A written artifact that a human has reviewed has already externalised the context worth keeping**, so the next phase goes to a fresh agent: a plan only its author can execute isn't a plan. A review finding sent back on the same artifact still goes to its worker.
- **Waiting stays out of the threads the user talks to.** CI polling, deploy watching and long live checks go to a watcher or a worker. No agent forks or copies itself to wait; it waits on a notification (a backgrounded blocking command such as `gh run watch`, or a Monitor until-loop), never by sleeping and re-checking across its own tool calls.

## Phases

Four questions per unit of work: **problem → design (only when needed) → plan → implement → verify.**

- **Problem** is its own step, not a preamble to design. A request usually arrives as a proposed fix, which assumes the problem is what it first looked like. State three things and check them with the user: the problem or opportunity in one sentence, what evidence says it is real, and what would be different once it is solved. If any can't be answered, closing that gap is the first piece of work.
- **Design** answers the *next* question: given the problem, which of several shapes is right. Run it when the shape is genuinely open or the cost of getting it wrong is structural; skip it when the shape is settled. Its output is the decision and its reasoning, written down — not code.
- **Plan** agrees scope before code. Iteration-sized work gets a plan doc the user reviews; a small fix gets a sentence or two. This is where the user's input concentrates: constraints, priorities, taste. Name the top risks and, for anything that ships behaviour, **the lever that undoes it** — a revert, or a parameter the change already reads. A flag that keeps the old path runnable beside the new is a second implementation (`principles.md`, "One concept, one implementation") and needs a stated reason. A change whose rollback is "work out what to do when it breaks" has not been planned.
- **Implement** runs autonomously through the agreed scope. Tests first (red) → minimal implementation (green) → refactor; gates green; checkboxes ticked when their tests pass (a checkbox records a fact, not an approval). When a test has wrong expectations, fix the test rather than bending production code around it. When a blocker forces a plan change, update the plan and keep going; don't ask "continue?". Say so in a line when something changes the plan or the risk. Interrupt only for a scope decision the plan doesn't answer, a destructive or outward-facing action, or a blocker unresolvable from the repo; everything else batches to the report.
- **Verify** checks the gates ran green and could have failed, closes with a review, and reports: outcome → evidence → deviations from the plan → batched questions.

**A phase boundary is not automatically a checkpoint.** Ask what the user's answer would actually change: when the next phase is theirs to steer — scope, priorities, taste — stop and show the artifact. When it isn't, carry through into the next phase and show them the result, because a gate that only ever gets approved is a delay charged to the person waiting. Say which boundaries you passed without stopping, so anything they would have commented on can still be picked up. **Outward-facing actions are never covered by this**: each waits for its own go, and a run of approvals is no evidence the next one is granted.

**This is not a waterfall.** They are questions to keep answered, and the arrow runs both ways: what is cheap to build informs which problem is worth solving, a design pass that measures its options often finds the problem was not what was stated, implementation sends you back to the design, and a review at any gate can reopen an earlier one. Moving backwards when evidence arrives is the process working.

Being allowed to go back is the easy half; **noticing that an assumption broke** is the hard half, because an unstated assumption cannot be contradicted — it just quietly makes everything downstream wrong. So when a step hands off, name in the plan doc or the brief what it is assuming that the next step could disprove. Then, when something small and odd turns up later, check it against that list before explaining it away.

**Four questions at every boundary**, asked out loud rather than left to be noticed — noticing is exactly what stops happening under momentum.

- **What would falsify this, and who would notice?** The assumption list above is the answer; an empty list is itself the finding.
- **Who hasn't been asked whose objection would change the answer?** Not everyone relevant — only the ones who could move the decision.
- **Is this the second or third fix at the same seam?** Make it a lookup rather than an intuition: `git log` the files being touched and read what the earlier fixes there were for. A second patch at one seam is a design (`~/.agents/principles.md`, "Ask what you are compensating for").
- **Has anyone actually used it?** Not "do the gates pass" — has a person or an agent operated the surface end to end. This is the one that never fires on its own.

## Debugging starts at a reproduction

For a reported defect the **problem** phase has a specific shape: the first artifact is a reproduction in the reported state, not a hypothesis and not a fix. Build the reporter's conditions rather than the convenient ones — their device and engine, their data volume, their configuration, a warm cache or a cold one. A measurement taken on a clean rig with everything enabled describes someone who does not exist, and everything downstream inherits that population. **"It does not reproduce here" is a result**, not a failure: it relocates the cause.

**Read the instrument before reasoning about the system.** The telemetry the product already emits usually knows the onset, and nobody looks. Then name what a measurement cannot see before believing it: a tool that collapses rows, omits a field or samples the wrong layer reports a confident nothing.

For a **regression** the first obligation is to find what changed. A redesign that would make the symptom go away is not a fix for a regression nobody has identified.

The reproduction then stays as the guard: turn it into a failing test before fixing (red-proof) and keep it as the regression guard, since fixes shipped without one recur.

## Measure it

- **Everything should be measurable.** Any mechanism that silently changes what happens ships with the counter that makes it visible, and a check that cannot run fails loudly rather than degrading to "pass" (`~/.agents/principles.md`, "Log for the debugging you will actually do"). Before merging, ask: if this misbehaved, what number would move, and is anyone emitting it?
- **Be evidence-driven from the start.** Collect metrics, quantitative or qualitative, *before* deciding. A number collected afterwards to confirm a choice already made measures the choice rather than the problem, and it agrees, because agreeing is what it was collected for.

## Delegation prompts

Agents see nothing of the conversation. Every delegation prompt includes:

- The full agreed design and decisions already made — the agent must not re-derive or re-litigate them.
- **Facts checked against the source, or marked as claims.** Most brief errors are a fact copied unverified from an earlier agent's report, or a guessed path. Root every path at the agent's worktree, or it may write into the base checkout.
- Pointers to the repo's instruction files (`AGENTS.md`/`CLAUDE.md`) and applicable conventions (commits, style).
- What to run (tests, linters) and hard boundaries: the agent commits locally, while pushing, merging and anything else outward-facing stay the main loop's. The standing exception is an agent that has to push in order to deploy or test its change, granted deliberately. Flag new dependencies in the report for sign-off.
- Environmental gotchas the last agent hit (a stale dev server on a port, a slow gate) — they travel between agents only via the brief.
- The report format, and keep it terse: files changed, decisions it made itself, test results, identifiers (SHAs, paths). Ask for a short factual report — default reports run long.
- **Whether the agent may sub-delegate, and where.** An agent handed a large scope will parallelise it, and by default it will do so inside the checkout you gave it — which is the collision above. Say explicitly: sub-delegate freely for read-only work, never for concurrent writes to one tree.
- **Ask what the brief got wrong.** Briefs carry errors — a stale path, a wrong name, an assumption that doesn't hold. Agents that say so plainly are far more useful than ones that quietly work around it, so make it a named line in the report format rather than hoping it surfaces.
- **Name the forks you expect, and leave a question path open.** At a fork the brief doesn't settle (an approach it didn't anticipate, the same error twice, unsure whether it is done), the agent asks one short question instead of guessing: it ends its turn with the question as its report (through the handback tool where there is one; say in the brief that a question is an authorised use of it, since the tool's own description rules questions out) and carries on when continued with the answer. The question names what it is deciding, the options and what it found. Answer from the context you hold, and pass up only what you cannot.
- **A wrong question is worse than a wrong sentence.** A sentence gets shot at; a question quietly bounds what anyone can find. "Does X get worse without the bonus" has its answer built in — ask which direction it moves. Before a brief goes out, check whether any question in it admits only one interesting answer.
- **Frame a measurement so a null result is a win.** "A flat curve is a fully successful outcome", said in the brief, is what makes a ruled-out column trustworthy. Otherwise an agent that finds nothing keeps looking for something.
- **Ask for evidence honesty explicitly** ("state plainly if the window gave you nothing"). It works.

## Trust boundaries

Verify *delegated* work before building on it: read the diff yourself and spot-check the one number or file that would falsify the report. Don't re-run the agent's suites, which proves the report honest but never the premise sound (below); check that they ran and could have failed. When a result fails your gate, take that piece back inline rather than iterating blind through re-briefs, and treat an agent that repeatedly fails gates as a brief problem before a model problem.

A green test is not evidence that the test exercised anything. When an agent reports a suite passing, check that the assertion *could* have failed — one that mocks away the thing it names, or returns before reaching it, reports success while doing nothing. It's the failure mode delegation is most prone to, because the report is honest and the number is real.

**A check must not degrade to "pass" when it cannot run** (`principles.md`, "Log for the debugging you will actually do"). The shape no reader catches by looking harder is output contradicting its own verdict: a 0% pass rate printed above "no regressions detected", exit 0. Another is a scoped run that matched nothing, such as `pre-commit run --files` handed a newline-joined string under zsh: pass a real argument list and confirm the output names your files.

**Independence of execution is not independence of assumption.** Re-running the gates catches a dishonest report; it cannot catch a premise the code and its tests share, because they were written together. A suite can be green and a red-proof can fail for the right reason while the whole series rests on an invariant the rest of the system contradicts. What catches that is a reader who saw neither the code nor the conversation, reading the source against what the system does elsewhere, which is why nothing ships without a neutral review.

**A completion notification can arrive before the agent's last writes land.** Confirm the tree has settled before reading or acting on it: compare a cheap signal (`git status --porcelain`, a file's content) twice a short interval apart.

An empty result is not evidence of absence either. A query against logs or telemetry returns nothing when the event never happened, but equally when it fell outside a silent retention window, or a filter was wrong, or the context pointed at the wrong account — none of which raise an error. Before concluding something never ran, establish that the query would have found it.

Verify cheaply, though: re-deriving the agent's whole analysis in the main loop spends exactly the context the delegation was meant to save. And don't stack blanket "double-check everything" instructions on your own work; the model already self-verifies, and redundant instructions cause over-verification.

## Verifying model-shaped work

Whenever a model sits inside the product's contract — not the agent building it, the model the product itself calls — the usual gates under-report, in ways that repeat.

- **Live runs beat green suites.** Every prompt or protocol design that passed its unit suite still broke on first live contact in some new way (models mangling long ids, echoing short keys, ignoring language rules). Budget a live-run and eyeball gate into any iteration whose contract involves a model.
- **Verify the signal before gating on it.** Before making behavior depend on a model-produced score, check the live distribution and read the actual scored items. A surprising score is a prompt to check for misconfiguration first (the grader's instructions, the test data or labels, the prompt under test, what the grader was shown), and where two graders disagree, read the disagreement against the material.
- **Read a scored item against the material it was given**, not only against its expectation. A low score has three causes that look identical: the subject dropped something the material held, the expectation asks for something the material never held, or retrieval lost it; only the first is a defect in the subject. The judge's recorded reason is model-written too, so check the claims a decision rests on.
- **Grade for invention, not only for form, on any generative step.** A schema or length check passes an answer that is fluent, well-shaped and wrong; a model given little to work with tends to fill the rest in with confidence rather than say so.
- **Verify against reality, not a proxy.** Measure the exact interaction reported, not an adjacent path. Know what emulation can't show (touch feel, fixed-overlay geometry, engine-specific events, system fonts): assert against the environment's own rendered ground truth, never a fixed "fits at width X". Where only real hardware can decide, ship the hygiene fix, state the limit, and hand the check back.
- **The user's bug report IS the repro spec** ("Debugging starts at a reproduction").
- **E2E determinism is a contract:** three consecutive green runs before shipping suite changes; flakes get root-caused (they have exposed real product races), never retried into silence, and that includes ruling out load from a parallel lane. Specs change FORWARD, with the intended semantics itemized in the report.
- **Screen cheaply before the full evaluation.** A small, single-repeat run can rule out an alternative (a reasoning level, a model tier, a prompt variant) before the full suite with repeats and blind grading is spent on it. Reserve the full run for the alternatives still in contention.
- **Iterate on a targeted subset at a high trial count, not the whole suite once**, when a change needs *resolution* on a handful of cases. Run everything once before merge.
- **A fix for a reported behaviour that fails on device twice**: stop tuning, re-derive, and expect the win to be REMOVING the mechanism (`principles.md`, "Ask what you are compensating for").

## What reaches the user

What reaches the user is in the global instructions, "Calibrating what surfaces". The delegation-specific half: **anything an agent writes for a third party** — PR descriptions and comments, ticket bodies, chat drafts — tends to narrate the work it just did, so several agents turn a PR into a changelog of the session whose later entries contradict the earlier ones. Don't have agents post their own summaries; have them report to you, and own the end-state framing yourself. If you do delegate the writing, brief the end state rather than the story (the `pr-description` skill carries the rules for that surface).

## Commits across a long session

- **Tell agents to commit after each coherent step**, not at the end. Long runs get interrupted, and uncommitted work is lost work — say it in the brief, because saving it all for the end is the default. An agent that owns its checkout writes its own commits: it knows what it changed, which is what an honest commit message needs. Two writers sharing one index is the hazard, not delegated committing.
- **Commit only your own changes.** While agents are live, run `git status` + `git diff --staged` before every commit; after any conflicted stash apply, `git reset` before adding anything. Shared files (lockfiles, generated artifacts, anything under evaluation) are the classic traps.
- **Keep the commits that earn a place in history** — one coherent change, reasoning in the body, the kind someone later runs `git log` to understand. A review finding fixed as its own commit usually qualifies; reviewers read the branch in that order. Fold the artefacts of how the work happened: a format-only commit a hook produced, a typo fix to its own predecessor, a comment corrected two commits later. After folding, confirm it changed no content: `git rev-parse HEAD^{tree}` before and after should match.
- Fixups, autosquash, what may be rewritten and how it is pushed are in the global instructions, "Git Conventions".

## Reviews

Close each meaningful unit of work — an iteration, a phase, a coherent set of changes — with a review before calling it done; skip only trivial or mechanical changes. The skip covers this per-unit pass, not shipping: nothing ships without a neutral review. When the head moves after a review, the next one reviews the delta (a `git range-diff` across a rebase), unless the delta reworks the change. A repo's or session's own review guidance comes first; this is the floor.

Never review work from the conversation that produced it. Spawn a neutral agent that has read neither the code nor the conversation behind it. **How much you may tell it splits by whether its review votes.** Where a verdict gets posted, approves, or routes a reviewer, its entire input is the artifact reference plus the review instructions: no framing, focus hints or expected outcome. Where nothing is posted and nothing votes, saying what the unit was for, what to weight and what is settled saves a pass spent rediscovering context. Never supply the answer you expect.

The conversation knows what the neutral agent can't see — where the design felt fragile, which constraints were negotiated, what almost went wrong. Use it for the complementary pass: decide what else to exercise (targeted tests, evals, checks), run it now, and promote what has lasting value into the suite or CI.

**A reviewer that returns nothing has not passed.** Re-run it, and where it dies again say so: a check that cannot run, applied to a review.

**What to run is a function of what the change touched**, and the same mapping picks the design lenses at the start — one rule at both ends, so nobody has to remember which review this deserves.

**Where a role holds the perspective a lens judges by, that role's standing brief is the bar**: read `~/.agents/skills/team/roles/<role>.md` on top of `reviewer.md` there and judge against it, including for a role invented later. An entry below describes itself only where no brief holds it.

- Correctness is the floor and always runs.
- Untrusted input, authn/authz, secrets, a new boundary → a security pass.
- Deploy, CI, cost, data retention → an infra pass.
- A plan that ships behaviour → a **failure-mode** pass, against `roles/operator.md`, before the user approves the plan and before anything is built: how does this fail in production, asked of the lever that undoes it, a dependency down or slow, two things running at once, a side effect that cannot be taken back, and old and new versions live together. A red pass earns one revision; a second red goes back to the user.
- A new seam, or a second implementation of a concept that already exists → an architecture pass, against `roles/architect.md`.
- Anything a future reader has to navigate → conventions and repo ergonomics.
- A shape that grew past what was asked for → a **cut pass**, biased toward removing, whose test is whether the user asked for it. On a small diff it rides with the prose pass.
- A number anyone will act on → a **measurement** lens that owns the population and the rig. Ad-hoc measuring is where wrong denominators get minted.
- Prompts, evals, judge models, quality gates, test datasets, retrieval behaviour → an **AI-quality** pass, against `roles/ai-engineer.md`: what was verified live rather than assumed ("Verifying model-shaped work" above).
- A new capability, or a behaviour someone will notice changing → a **product** pass, against `roles/pm.md`: does the premise still hold now the thing exists. Purely technical work earns none, having no premise to test.
- A user-facing surface → **two** passes, and they are not the same thing. A **UX review** judges the shape by reasoning — hierarchy, affordance, flow, wording — against `roles/ux.md`. A **product critic** operates the running thing and reports what actually happened; only it finds the clipped popover and the word that reads wrong, and it has no brief, since no role practises operating the built thing.
- Text in a language the round has not been working in → **a reviewer writing in that language**, wherever the text sits: a prompt, a UI string, a document, a ticket or a deck. Translated strings can be correct and still read as translated; only someone thinking in the language catches a compound spelled as two words or a term nobody uses. Worth calling now and then even when nothing changed, since copy drifts one string at a time.
- Prose gets its own pass, and it must be allowed to delete: does this read like a log of events, does something else already say it, can it be shorter. **Run it as its own agent** — bundled into another review (the cut pass aside, on a small diff) it loses, because prose defends itself in the act of being read. **The diff is the scope**, comments and docstrings included; a brief that lists files narrows it, so report what it left out. Form the expectation from the diffstat *before* reading the justifications, and ask what the shortest version carrying the load-bearing content looks like, not whether this one is justified.
- **A doc that names the person the work is done for has a defect, and it is rarely only the phrasing** (`principles.md`, "Reasoning over conclusions in docs"). A sentence built around who decided something is usually a narrative entry to replace with what is true now, and a recorded decision whose only evidence is the attribution needs checking against the code before it is kept: an agent writing down its own wrong reading of what someone wanted is the common way a doc acquires a decision nobody made.

**The outer loop.** Everything above attaches to a change, and some rot doesn't. Run a step-back pass that examines the product rather than the diff — UX, architecture, infra, CI, plans, docs — sized to whatever has moved since the last one. Drive it by trigger rather than calendar: before a large change, which is the cheapest moment to discover the shape is wrong and the one that never happens on its own; after one lands; and a floor of N iterations so it cannot drift indefinitely.

## Model and effort choice

- **Settle model and effort before a job or agent starts, from what the work needs**: recommend it to the user for a session, pick it when spawning a subagent, and treat a change mid-job as the exception, for work that turned out different from how it looked. Judgment-heavy or long-horizon work (deep architectural planning, gnarly debugging, adversarial review, a long multi-checkpoint session) earns a recommendation above the default, and routine work the offer to step down. Pick the lever by what will limit the work: more effort helps work on the right track but thin (steps skipped, verification cut short); a stronger model, when one exists, helps work that keeps missing the shape. Compare cost per result, not per token: where a miss costs a round trip and rework, one pass that lands is cheaper. A well-specified job that still warrants an Opus-class subagent (a scoped implementation against an agreed design, a rebase, a fix pass on named findings) runs at `effort: "medium"` on the Agent call (forks ignore it), since the provider reports this generation's medium matching the last one's high on coding; judgement-heavy or open work keeps at least the session's level. Effort is the lever that goes unpulled: a persisted setting tops out at xhigh, so `max` is a per-session choice.

**Pick each subagent's tier deliberately rather than inheriting the session's, and the discriminator is not the role — it is whether the output is checkable by something that is not another model.** Where the work is verified deterministically — a grep that must come back empty, a test suite, hooks, a build — a weaker tier is fine, because being wrong is caught immediately and for free: a mechanical rename sweep whose correctness a clean grep establishes is that case. Where the output is a judgement nothing mechanical can check — a design, an assessment, a review, "is this the right shape" — pay for the strong tier: an architecture review's findings are verifiable by nothing but another reading, and being wrong costs a round trip plus the rework, usually invisibly until much later. **The orchestrator is always the strong tier**: it holds scope and decides what reaches the user, and neither is checkable.

How that lands on today's tiers: mechanical, well-specified work whose correctness a gate establishes (scaffolds, fixtures, config, sweeps) → Haiku-class; standard implementation and research → Sonnet-class; algorithm-critical or judgment-heavy pieces that can't stay inline → Opus-class. **A frontier-class tier, meaning anything above Opus-class, never goes on a subagent without the user's specific go.** The one shape where asking for that go is worth it: a subagent that is both long-horizon and producing a judgement nothing mechanical can check, deliberately not held inline. The discriminator is the rule; this mapping is reasoning rather than measurement, and only where it currently lands. As of 2026-09-28 Opus-class is the strongest useful tier: Opus 5.5 beats Fable 5.1 across the board, faster and cheaper (the figures are in `~/dotfiles/docs/agent-setup-retune.md`); re-check at the next release.

## Improving the setup

- **Promote or it rots.** Plan docs and result notes are working artifacts for the run. Anything future-load-bearing (semantics, invariants, gotchas, "why not X") gets promoted into a canonical home, where the question will be asked, as part of closing the work; an archive or changelog takes it off that path. Promoting into an instruction file is an edit, not an append: fold the rule into the passage that already covers its subject and cut what it makes stale or duplicate, since a file that only grows is read less.
- **Fold friction into the setup, in the same run.** When a run hits friction — a git-flow accident, a model tier under-delivering, a test gap that let a regression through, an ambiguous instruction — fold the lesson into the relevant config, docs or instructions before the run ends. The same goes for a small defect noticed in passing (a doc claim no longer true, a fixture that cannot exercise its subject, a command that silently does the wrong thing): FIX IT IN THE RUN rather than handing it back as a finding. The test is whether it is obvious and needs no human decision, not whether it was in scope. List these changes at the end of an autonomous run.
- **Never size the work to avoid review attention.** That a change will flag a review lens, escalate to a human, put the branch on an infra or deploy path, or make the PR longer is not a cost to weigh against doing it: escalation is the gate working. **The infra case is the one that gets rationalised as prudence**: leaving a config, alert or pipeline file untouched because editing it triggers a heavier check ships a change whose own guardrails still describe the world before it. Deferring to a follow-up is legitimate on scope, never on the quieter review it buys.
- **Reconsider the autonomy when results keep getting rejected.** If work that ran unattended is work the user sends back at the end review, tighten toward step-wise check-ins for that kind of task rather than re-briefing harder.

## Living sessions

- Before an autonomous stretch: confirm scope and batch clarifying questions in ONE round, then run (interruptions as under "Implement").
- Durable learnings go to versioned docs (instruction files, skills, tickets) as they happen, not chat history, which gets summarized away.
- When a compaction or a fresh session is coming, the `handoff` skill covers the prompt pair that carries the work across — and what belongs on disk instead of in a prompt.
- Keep load-bearing state (task lists, decisions, open questions) in files the session can re-read, so the conversation surviving a compaction doesn't lose the plot. That is also what makes a run interruption-proof: an agent killed mid-run resumes from a short message stating the *disk* state — checkboxes, `git status`, which tests were red — with zero rework. Corollary for research agents: have them write the deliverable file incrementally, never only at the end.
